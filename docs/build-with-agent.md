# 让当前 Agent 直接构建 Wiki

默认任务是把完整来源整理成[文件契约 V2](wiki-format.md)。不接 LLM API，不要求安装模型、数值聚类或特定 Agent CLI。当前 Agent 用自己的文件工具读原文、提取和分类，写出规范文件；标准库脚本渲染并核验。

## 来源与准备

已有 Markdown 时直接使用，先枚举文件、确认作者和范围。不要把标题列表、摘要或截断正文当作完整来源。记录缺失类型、日期或正文，不声称抓取全量。

只有主页 URL 时，可选安装仓库并调用已有爬虫取得原文；显示昵称不是唯一标识：

```powershell
python -m pip install -e .
python -c "from zhihuer_wiki.crawler import crawl; import json; print(json.dumps(crawl('https://www.zhihu.com/people/URL_TOKEN', 'outputs/demo/raw', max_items=20), ensure_ascii=False, indent=2))"
```

上例最多 20 篇用于试运行，不能宣称全量。函数为 `crawl(user, out_dir, *, max_items=None, storage_state=None, kinds=('answer', 'article', 'pin'), delay_seconds=1.5)`。需登录访问时，由用户在本机运行 `python -m zhihuer_wiki login`，再将本地状态文件路径传给 `storage_state`。不要读取、展示或向模型输入凭据，也不绕过平台挑战。按返回的范围与限制决定后续材料范围。

`build --agent manual`、`next`、`submit` 属于[可选旧 V1 工作流](workflow.md)，不会自动构建 V2。不要为取得原文启动整套旧流程。

创建新的版本目录，复制完整 UTF-8 来源到 `wiki/sources/`，建立 `sources.json`，从实际文件字节计算 SHA-256。保留完整原 Markdown，元数据单独存放。发布后的来源不能通过改写来“修复”引文；新来源或修订进入新版本目录。

## 先提取完整条目

逐篇阅读完整原文，记录完成范围；独立来源可以分别提取，不必等待聚类或预先决定全部主题。保留具体表达，不只挑代表金句。长文超过预算时使用有覆盖记录的分段，检查跨段条件，不能静默丢掉尾部。

按契约写 `entries.json`：稳定 ID、doc_id、日期、精确原话、转述、条件。每篇可能产生多条，也可能没有适合的表达；记录空结果与原因，避免无声遗漏。保留相反或历史表达，区分本人立场与引述、假设、反讽。程序核对字符串，Agent 判断语义。

## 根据真实上下文预算分类

分类读取完整条目，包括原话和条件，不能只看标题或样本。先准备实际序列化输入，再计算或保守估算 token，包括指令、完整已有目录、ID 归属和本轮全部新条目。结合真实上下文容量、已有对话、输出和推理预留确定批量；输入通常可占可用上下文约 50%–70%，这是预算建议，不是完成标准。

只有模型实际支持且整份准备输入能够容纳时，才考虑约 250k token 的大批。不能只看标称上下文就无条件塞 250k，更不能只估算新增原文而忽略目录、成员关系与输出预算。放不下就减批或分波，保持条目完整，将状态存文件以便继续。

采用累积分类：

1. 首波按具体对象与问题生成共享目录，归属本轮全部条目。
2. 后续波次读取**此前完整主题与页定义、全部旧条目 ID 与成员关系**，加上本轮全部新条目的完整记录。合并或重解释旧页时，从归档按需读取旧条目全文。
3. 优先复用问题页；同义页带着原成员合并，过宽页基于完整成员拆分。保持旧 ID、新 ID 完整覆盖。
4. 每波写回一份累积目录与归属，最后全局检查。不要每波另造互不相干的小树，或只把批次目录并排堆起来。

分类由 Agent 判断。可选预分组不能成为输出契约或提取的前置依赖。

## 两层导航怎样安排

主题 → 具体问题页两层。两层的 `scope` 写清对象、边界与关键词，帮助读者判断能支持什么任务。页内保留完整条目卡，导航摘要不替代证据。

页大小按可读性和 token 量调整，通常可从每页约 8–25 条开始；很长的条目更早拆页。每层约 20 个主题/页可作为检查目录过宽的软提示，不是固定 `20×20×20` 容量或硬上限。不为凑数合并不同问题，也不普遍一条一页；小语料或孤立问题可以少于建议数量。

同题相反观点放在一起并保留日期、条件，不用中性概括抹掉差异。重组改变导航归属，不改写来源或静默删除条目。检查孤立条目、重复主归属、同义碎页及无法帮助定位的宽泛范围说明。

## 检查与发布

从仓库根目录运行：

```powershell
python scripts/wiki_folder.py render --wiki ./outputs/demo-v2/wiki
python scripts/wiki_folder.py validate --wiki ./outputs/demo-v2/wiki
```

检查真实 index → topic → page → source 链，确认页包含全部成员的完整卡片，链接打开完整来源。结构核验不能替代提取覆盖和语义审查。报告输入与处理范围、未知日期、抓取限制、尚未解决问题；不宣称未经验证的分类或回答质量。

通过后交付完整新版本文件夹；来源、规范 JSON 与导航一起搬迁。保留批准过的版本，更新在新目录完成，不在查询中自动改写。

新增材料可读取原有来源索引、完整目录和归属，只提取新材料，再累积合并与重组。保留原来源和条目 ID；修订来源使用新身份并保留旧证据，不覆盖批准过的来源。这是 Agent 执行的更新方法，不是已实现的自动增量 CLI。

## 可直接复制的任务

```text
读取 .agents/skills/zhihuer-wiki/SKILL.md 和 docs/build-with-agent.md。
将 ./raw 中这位作者的完整 Markdown 整理到新的 ./outputs/author-v2/wiki。
按 docs/wiki-format.md 写 index.json、entries.json、sources.json 和完整来源。
用你的文件工具提取与分类，无需聚类或启动旧 V1 job 循环。
逐篇记录覆盖，保留精确原话、日期、条件、相反表达和稳定 ID。
按实际 token 预算累积分类：后续波次保留完整已有目录和全部旧归属，
合入本轮完整新条目，避免每波分裂出新树；目录两层、页大小自适应。
运行 render 与 validate，检查真实导航到原文链；通过后交付完整新文件夹，
报告材料范围与未解决缺口。保留批准过的旧版本。
```

最小完整虚构资产见 [samples/wiki-v2](../samples/wiki-v2/index.json)。其中条目数量仅用于演示契约，不是推荐的正式分页策略。
